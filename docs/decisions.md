# Decisions

- Native chat templates receive only a single unchanged question, without a system prompt. This meets the strict question-only condition and keeps English/French wording intact.
- vLLM 0.17.0 is already installed and contains Apertus and Llama implementations. Execution is currently enabled only for the complete Llama checkpoint. Architecture support does not establish GC model identity or completeness.
- Four 40 GB A100 GPUs provide enough aggregate memory for roughly 132 GiB BF16 weights plus modest inference overhead. Eager mode, max_num_seqs=1 and an 8192-token context avoid graph memory growth. This remains subject to actual allocation smoke testing. No quantization or checkpoint substitution is introduced.
- Greedy decoding uses temperature zero and seed zero. Native EOS IDs, including Llama end-of-turn IDs, stop generation. Hardware/kernel reproducibility is not guaranteed bitwise; versions, prompt and parameters are recorded.
- Atomic JSON checkpoints simplify per-question recovery and preserve failed attempts. JSONL is generated as a coherent export rather than appended unsafely during worker crashes. The fingerprint namespaces model metadata and decoding/input identity.
- A 1,024-token response limit is the common baseline. Truncated answers retry with 2,048 tokens, with the actual budget recorded. Outputs still truncated after retries remain unresolved, not successful. Questions never truncate.
- No weights are downloaded, copied, changed or substituted. Expanded research followed a documented evaluation launcher to complete GC and Apertus snapshots in the alternate abm002 cache. Their exact revisions are pinned, and the official published GC model card verifies the matching Apertus parent. Initial config-only entries remain rejected.
- Slurm low-priority requeue policies are respected; unrelated running jobs and their environments are untouched. Acknowledgements persist to avoid accidental duplicate submissions.
- The system workbook library is copied locally for the worker because its existing inference runtime lacks openpyxl. No package is installed into a shared environment.
- A partial export is useful for checking the laptop handoff schema, but does not satisfy Stage 1. A strict final-export gate enforces all 2,268 successful responses.

- vLLM IPC sockets must use a short temporary directory (`/tmp/caneval-$SLURM_JOB_ID`), because Linux Unix-domain socket paths have a 107-character limit. Initial job 11815905 exposed this during engine startup; replacement job 11816009 uses the corrected path.

- Llama's upstream tokenizer template injects a fixed July 2024 date and December 2023 cutoff in a system block even when supplied only a user message. The effective template therefore uses its same supported BOS/user/end-of-turn/assistant markers with no system block. This enforces the user's strict question-only clarification; it is explicitly pinned and recorded rather than silently modifying the prompt. No request uses reference, context or scoring information.

- Hugging Face tokenizers can store native templates in a separate `chat_template.jinja`, not only in tokenizer_config.json. Discovery recognizes and hashes either representation, with regression tests. For both Apertus-family models, question-only role templates omit automatically added system identity/date/cutoff and developer capabilities text.

- User cancelled separate smoke inference and its reload overhead. `configs/execution.yaml` disables it and the full-generation smoke gate is removed. Worker scripts now invoke full generation directly. Existing GC/Apertus workers were promoted at a CPython pending-call safe point by changing their selected/pending lists in place while loading, with an audited acknowledgement. The active Llama full-run process was not restarted. Model/input fingerprints and decoding conditions remain unchanged.

- Latest user override supersedes the earlier truncation-retry decision: save all emitted text and continue after a token limit. Keep `truncated=true`, explicitly mark `accepted_truncation=true`, and export the answer rather than discarding it. Success now denotes captured generation output, not necessarily natural EOS completion. Existing raw attempts remain unchanged; accepted top-level records retain their flags. All three active workers received this store-policy update at interpreter safe points without reloading weights.

- Latest user request authorizes the required engine restart to enable batching. A sequence ceiling of 64 removes the previous artificial single-request limit. Actual in-flight count is adaptive, using 95% of the minimum measured KV-cache token capacity across tensor-parallel workers, with block-rounded prompt plus full output reservations. This aims to maximize safe concurrency without KV overcommit or question truncation. Eager execution and the existing 94% GPU memory allocation remain unchanged.
- The scheduler loop sends one separately tokenized question per request, accepts out-of-order completions by question ID, saves each completion immediately and refills freed capacity. Error-only retries preserve prior attempts; token-limit outputs are retained per user instruction. Batch runtime metadata and source/config fingerprints remain traceable.
- Controlled restarts preserve current Slurm jobs and GPUs: a one-time interpreter-safe callback requests graceful draining and registers an exit handoff that closes the old engine and execs the new batch-enabled worker. No live GPU-buffer resizing is attempted. Completed responses are reused across the topology change; numerical kernel differences are recorded through run/execution metadata.

- The first cache-metadata RPC was rejected by vLLM’s serialization guard. The pipeline now reads the coordinator’s measured GPU KV-cache token capacity from the current job log and uses its cache block size for reservations, without changing serialization security settings. GC/Apertus initial batching starts ended before producing new answers and were resumed as jobs 11817121/11817122. Llama’s pending batch-capacity lookup was repaired in place.
